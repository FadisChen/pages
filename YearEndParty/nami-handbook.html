Nami 尾牙主持人手冊

一支 VRM 虛擬主持人，怎麼靠兩台裝置的 WebRTC 配對收音、靠 Gemini Live API 即時聽說、再靠 function calling 把「說話」變成表情與動作。這份文件拆解三條主線的實際協定與程式邏輯，附上可對照原始碼的關鍵片段。

PeerJS 1.5.4 · WebRTC DataChannel Gemini 3.8 Live · BidiGenerateContent Three.js · @pixiv/three-vrm Vanilla JS · EventBus
stage.html 投影端筆電

顯示 VRM、連線 Gemini、播語音，畫面乾淨無控制項。

operator.html 工作人員手機

push-to-talk 收音、Rundown 環節按鈕，不連 Gemini。

index.html 單機測試

上面兩者合併在同一頁，方便一人快速驗證邏輯。

    本篇目錄
      01

      整體架構：三個角色，兩條連線

      系統裡永遠只有三個會「說話」的角色：手機（收音／下指令）、投影端筆電（VRM + Gemini + 音響）、Gemini Live（大腦與聲音）。手機與筆電之間是 WebRTC 直連；筆電與 Gemini 之間是一條 WebSocket。PeerJS 的雲端伺服器只負責幫兩台裝置「牽線」，牽好之後就退場。

      兩機模式下，音訊經過的路徑是「手機錄音 → WebRTC DataChannel → 筆電轉交 Gemini」，中間沒有經過 getUserMedia 的 MediaStream track、也沒有 Opus 編碼再解碼——因為 Gemini Live 吃的本來就是 16kHz PCM16 原始位元組，手機端直接切好封包送過去最省事也最不失真。單機模式（index.html）則直接跳過 WebRTC，同一支 microphone.js 把收到的 PCM 直接交給同頁面的 GeminiLiveClient。

      1.1檔案結構與職責

      模組職責
      webrtc-link.js房號、ICE 設定、Rundown 環節清單、operator↔stage 訊息契約——雙邊都 import 同一份，避免格式漂移。
      live-session.jsGeminiLiveClient：Gemini WebSocket 連線、回合、tool call、重連、session resumption。
      host-config.js共用模型名稱與系統提示詞組裝，避免單機與投影端人設漂移。

      avatar-gestures.jsplay_avatar_gesture 工具定義、程序化動作曲線、播放佇列 AvatarGesturePlayer（10 種動作）。

      02

      WebRTC：手機與投影端怎麼配對

      這裡的「WebRTC」指的窄一點：只用一條 RTCDataChannel，不建立語音用的 MediaStream／RTCPeerConnection track。PeerJS 把 SDP/ICE 交換包成 Peer／DataConnection 兩個物件，省掉手刻 signaling server 的麻煩。

      2.1被動端與主動端

      stage.js 開一個固定房號的 Peer 等人連進來（被動端）；operator.js 掃 QR code 拿到房號後主動撥號 peer.connect(roomCode, {reliable:true})。整個交握全部經過 PeerJS 的公用雲端 broker 轉發，一旦兩端的 DataConnection 進入 open，之後的資料就走 P2P，不再經過 broker。

      2.2為什麼音訊也走 DataChannel，不開 MediaStream

      一般語音通話會用 getUserMedia() 餵進 RTCPeerConnection 的 audio track，但那條路徑會把音訊丟進瀏覽器的 Opus 編碼器，抵達對端還要再解碼、還可能被瀏覽器悄悄套用它自己的 AEC/AGC。這裡反過來：手機把麥克風收到的音訊在 AudioWorklet 裡直接切成 16kHz mono PCM16、每包 ≤640 bytes（20ms），和 PTT 起訖、環節切換這些控制指令共用同一條 reliable/ordered DataChannel送出。共用同一條有序通道是關鍵：它保證「最後一包 PCM」一定比「放開按鈕」的訊號早到，Gemini 不會誤判使用者提前講完。

      2.3訊息契約（webrtc-link.js）

      方向type內容說明
      operator → stageptt{active:true|false}AudioWorklet 產生的發話起訖
      operator → stageaudio{bytes:Uint8Array}16kHz mono PCM16 LE，每包 ≤640 bytes
      operator → stagesegment{id:"lucky_draw"}切換 Rundown 環節
      operator → stagenote{text:"..."}現場備註／文字訊息，會轉成 sendText
      stage → operatorstatus{state}idle / listening / thinking / speaking / interrupted
      stage → operatorconnection{status}connected / connecting / reconnecting / failed / offline
      stage → operatortranscript{role,text}使用者／模型逐字稿（部分更新）
      stage → operatorturn-complete–清除本輪逐字稿合併狀態
      stage → operatorsegment-ack{id}確認環節已套用

      2.4壅塞保護與已知風險

      手機端每送一個麥克風封包前會先檢查佇列是否已經塞車：

      operator.js
      if (dataConn.bufferSize > 50 || dataConn.dataChannel?.bufferedAmount > 64000) {
  // 直接斷線重連，而不是繼續送過期的音訊/指令
}

      一旦網路壅塞就主動斷線重配對，避免 Gemini 根據「過期的」PTT 片段做出反應，比繼續硬塞更安全。

      已知風險：ICE_SERVERS 目前只設定 Google 的公用 STUN，沒有 TURN。若會場 Wi-Fi 對同網段裝置做「用戶隔離」（許多飯店/場地預設如此），純 STUN 可能打不通，正式上場前務必在實際場地網路先測一次配對，並準備好 TURN 憑證（例如 Twilio NTS、metered.ca）填進 ICE_SERVERS。
      03

      Gemini Live：一條 WebSocket，手動 VAD

      GeminiLiveClient（live-session.js）直接對 wss://generativelanguage.googleapis.com/.../BidiGenerateContent 開一條 WebSocket，用官方 Bidi 協定手刻，沒有透過任何 SDK。

      3.1setup 訊息：關掉自動語音偵測

      連上後第一件事是送 setup，裡面最關鍵的一行是把伺服器端的自動語音活動偵測（VAD）關掉：

      live-session.js — setupMessage()
      realtimeInputConfig: { automaticActivityDetection: { disabled: true } },
sessionResumption: this.resumptionHandle ? { handle: this.resumptionHandle } : {},
contextWindowCompression: { triggerTokens: 8000, slidingWindow: {} },
inputAudioTranscription: {},
outputAudioTranscription: {},
tools: [{ functionDeclarations: [AVATAR_EMOTION_TOOL, AVATAR_GESTURE_TOOL] }],

      尾牙現場的背景音樂與人聲很容易讓伺服器自動 VAD 誤判講話起訖，所以改成完全手動：工作人員按住按鈕才送 activityStart，放開才送 activityEnd——按鈕本身就是「輪到 Gemini 說話」的觸發器。輸入／輸出逐字稿都開啟轉錄，逐字稿只是診斷用途，不代表模型內部真正理解的內容。

      3.2一次完整回合的訊息流

      3.3斷線、重連與 GoAway

      三個機制一起處理「連線不會永遠活著」這件事：

      • Session resumption——伺服器每次回 sessionResumptionUpdate 就記住新的 resumptionHandle，下次連線帶著它重建 context，不用重講一次系統提示詞與歷史。
      • GoAway——伺服器要求換線時只設一個旗標，不會立刻斷線；reconnectWhenIdle() 會等目前輸入、回覆、播放都結束才真正關閉 WebSocket，避免把正在說一半的句子腰斬。
      • 失敗重試——連線失敗時以 1s / 2.5s / 5s 遞增重試，第 3 次仍失敗才回報 failed，讓 UI 顯示錯誤並釋放麥克風。
      Context window compression 設定 triggerTokens: 8000，讓伺服器在對話累積到一定長度時自動壓縮上下文——這不等於連線不會斷，長時間跑尾牙全場的可靠度仍需要實機測試（見第 07 節）。
      04

      Function Calling：把說話變成表情與動作

      Gemini 3.8 Live 支援非同步（NON_BLOCKING） function calling。這裡定義了兩個工具，讓模型在生成語音的同時，「順手」決定 Nami 該做什麼表情、動什麼動作；工具結果以 WHEN_IDLE 排程回報，避免阻塞目前的語音回合。

      4.1兩個工具的定義

      avatar-emotions.js — set_avatar_emotion
      {
  name: "set_avatar_emotion",
  behavior: "NON_BLOCKING",
  parameters: {
    type: "OBJECT",
    properties: {
      emotion: {
        type: "STRING",
        enum: ["neutral","happy","sad",
               "angry","surprised"]
      }
    },
    required: ["emotion"]
  }
}
      avatar-gestures.js — play_avatar_gesture
      {
  name: "play_avatar_gesture",
  behavior: "NON_BLOCKING",
  parameters: {
    type: "OBJECT",
    properties: {
      gesture: {
        type: "STRING",
        enum: ["nod","shake_head","wave",
          "present","tilt_head","bow",
          "shrug","hand_on_chest",
          "salute"]
      }
    },
    required: ["gesture"]
  }
}

      兩個工具的 description 直接把「什麼情境用什麼值」寫進 schema 裡（例如：肯定用 nod、否定用 shake_head、道謝或道歉用 bow），這樣模型不需要額外的 few-shot 範例就能選對值；系統提示詞（host-config.js）再加一句限制：每個回覆最多各呼叫一次，不需要時不要呼叫，也不要拿工具控制嘴型或連續動畫——嘴型是 LipSync 引擎依音量分析算出來的（第 05 節），跟工具無關。

      4.2呼叫回合：驗證、套用、回應

      4.3被打斷時，動作要跟著取消

      使用者在 Gemini 說話中途按下 PTT 打斷時，伺服器會送 content.interrupted，同時可能送 toolCallCancellation。live-session.js 對這兩種訊號各自處理：

      • interrupted → 清空 suppressAudio／playbackPending，並把「本回合已用過一個動作」的旗標 gestureUsed 重置，同時發出 gemini.interrupted 讓 stage.js 停止播放、重置表情。
      • toolCallCancellation.ids → 轉發成 avatar.gesture-cancel，讓 AvatarGesturePlayer 依 id 把還沒播出來的排隊動作／正在播的動作直接取消，不會讓一個已經被打斷的回覆還在比手勢。
      05

      Avatar：VRM 怎麼「做出」表情與動作

      工具呼叫只丟出一個字串（"happy"、"wave"）；真正把它變成臉部與肢體動畫的，是 stage.js 裡的 VRMAvatarController，疊了四層動畫：呼吸/待機的程序化擺動、狀態機驅動的姿態、表情 blend shape 交叉淡化、以及一次性的動作曲線。

      5.1表情：blend shape 別名解析 + 交叉淡化

      不同 VRM 模型的表情 blend shape 命名不保證一致（happy 可能叫 Happy、joy…），載入模型後 resolveExpressions() 會用一張別名表把 5 種情緒與 5 個嘴型母音都解析成「這個模型實際的表情名稱」：

      邏輯名稱用途常見別名
      neutral / happy / sad / angry / surprised五種情緒（set_avatar_emotion）模型原生 VRM 表情名，或首字大寫變體
      aa / ih / ou / ee / oh五個嘴型母音（LipSync）mouthA、vowelA 等
      blink / blinkLeft / blinkRight眨眼eyeBlinkLeft 等

      套用表情時不是直接切換，而是每次 setEmotion() 記住「從哪個情緒來」，用 emotionMix（0→1，約 0.3 秒）在新舊兩個表情之間線性交叉淡化，臉不會在一個 frame 內突然切換。happy 額外乘上 mouthIntensity，跟嘴型共用同一組控制點，避免笑意和說話張嘴互相打架。

      5.2動作：程序化曲線疊加在骨骼上，不是動畫檔

      10 種動作完全沒有用任何 .vrma／骨架動畫檔，而是每種動作各寫一段以時間 t 為輸入的手刻曲線函式，直接輸出人形骨骼（hips/spine/upperArm/hand…）該疊加的 Euler 角度。例如揮手：

      avatar-gestures.js — sampleGesture("wave", t)
      const weight = smooth(t / .35) * smooth((duration - t) / .45); // 淡入淡出
const beat = Math.sin(t * Math.PI * 3);                        // 手臂擺動節奏
case "wave": return {
  rightUpperArm: [0, 0, -.08 * weight],
  rightLowerArm: [0, 2.7 * weight, (.2 + .1 * beat) * weight],
  rightHand:     [-1.51 * weight, -.28 * weight, .36 * weight],
};

      weight 用 smoothstep 在動作開頭與結尾各做一段淡入淡出，beat 用 sin 波製造揮手的來回擺動——每個動作都是這種「淡入淡出 × 節奏波」的組合，沒有任何一張姿勢是手動關鍵幀擺出來的。update() 每個 frame 把這組角度轉成 quaternion，乘（multiply）在既有的待機姿勢骨骼旋轉上，而不是取代它——所以動作播放時，呼吸、視線飄移這些底層待機動畫仍然同時在跑。

      播放時機由「正在出聲」決定，不是收到工具呼叫就立刻播：AvatarGesturePlayer.queue() 先把動作放進 pending，update(dt, playing) 每個 frame 檢查 playing（音訊播放器是否正在出聲），只有真正開始播語音那一刻才把 pending 轉成 active 開始計時——避免文字還沒轉成語音、動作卻先做完的錯位。等待超過 8 秒或本回合結束仍未播放，動作會直接被丟棄。

      5.3LipSync：即時音量頻譜 → 五個嘴型母音

      嘴型完全不靠 Gemini 傳的任何 viseme 資料，是純前端音訊分析：LipSyncEngine 掛在播放器的 AnalyserNode 上，每個 frame 讀時域與頻域資料，算出低/中/高三個頻段的能量平均，用一組簡單規則分類母音：

      stage.js — classifyViseme(low, mid, high)
      if (low  > mid * 1.2  && low  > high * 1.15) return "ou";
if (high > mid * 1.1) return high > low * 1.3 ? "ee" : "ih";
if (mid  > low  * 1.16) return "aa";
return "oh";

      整體音量（RMS）低於 .018 視為沒在說話、嘴型歸零；權重上升用 .38、下降用 .18 的不同插值係數，張嘴比閉嘴更快，聽起來才不會拖泥帶水。這個分類是頻譜能量的粗略近似，不是語音辨識，圖求的是「像在說話」而不是精準對嘴型。

      5.4五態狀態機：idle / listening / thinking / speaking / interrupted

      待機呼吸的幅度、頭部視線飄移的節奏，都會依目前狀態的權重（stateWeights，每態各自用指數平滑趨近 0 或 1）微調——例如 listening 時多一點點頭節奏，thinking 時頭略微側傾，speaking 時頭部隨音量做說話節拍。狀態轉換本身是一張顯式的合法轉移表，不是任意跳轉：

      事件總覽：EventBus 是唯一的接線方式

      三個入口頁面內部都用一個最小的 EventBus（on/emit）串接模組，GeminiLiveClient、VRMAvatarController、PeerLink 互相不直接持有對方的參照，只透過事件名稱溝通，方便個別替換或寫測試。

      事件發送方用途
      gemini.connected / gemini.disconnected / gemini.connection-lostGeminiLiveClient連線生命週期
      gemini.audioGeminiLiveClient模型回覆的 PCM 音訊片段
      gemini.user-transcript / gemini.model-transcriptGeminiLiveClient雙向逐字稿（診斷／轉發給手機）
      gemini.turn-complete / gemini.interruptedGeminiLiveClient回合結束／被打斷
      gemini.avatar-emotionGeminiLiveClient工具呼叫解析後的表情結果
      avatar.emotion / avatar.gesturestage.js 轉發 / GeminiLiveClientVRMAvatarController 實際套用的入口
      avatar.gesture-cancel / avatar.gesture-turn-completeGeminiLiveClient取消排隊動作／清 gestureUsed 旗標
      avatar.visemeLipSyncEngine即時嘴型母音與權重
      peerlink.connected / peerlink.data / peerlink.disconnectedPeerLinkWebRTC 配對狀態與收到的訊息
      07

      目前的限制

      • 抽獎、音效、AI 自動建議換環節等擴充工具還沒做；環節切換一律由工作人員手動觸發，Nami 不會自己宣布進入下一環節。
      • API Key 目前是開發測試模式，存在瀏覽器 localStorage，沒有做 ephemeral token；正式對外使用前需要處理金鑰保護。
      • ICE_SERVERS 只有 STUN 沒有 TURN，尚未在真實兩台裝置＋真實會場網路下測試過配對，上場前務必實測（見第 02.4 節）。
      • Context window compression 與 session resumption 能延長單條連線的壽命，但不保證整場活動不斷線；長時間運行的韌性仍待實機驗證。
      • LipSync 與情緒交叉淡化都是前端啟發式規則，不是模型直接輸出的表情/口型資料，效果與模型生成語音的節奏相關，非公式可完全保證。
